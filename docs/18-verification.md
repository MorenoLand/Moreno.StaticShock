# Verification

Correctness is a property of behaviour, not of a successful compile. This page describes the
verification ladder and the records that make it reproducible.

## 1. Identity

The manifest pins the target:

```sh
python static_shock.py manifest
python static_shock.py manifest --verify
```

It records the SHA-256, size, image base, entry, sections, imports and tool versions. A test run
that starts from a different binary is not comparable. Never commit the target binary; commit the
manifest.

## 2. Inventory

```sh
python static_shock.py inventory
python static_shock.py inventory --check
```

The inventory records every function, its size, category, name confidence, evidence kind and
unsupported-instruction status. `--check` fails if an unsupported address is not in the inventory
or if the target digest changed.

## 3. Source-built fixtures

Use small programs whose source you own. Compile them in CI or locally; never commit the binary.

- one function per semantic area: flags, shifts, division, x87, SSE, string ops
- a PE with imports, callbacks and a window, to test the ABI bridge
- a known-bad input for each graceful failure (unsupported instruction, missing import)

A fixture is useful when its expected output is independently known, not when it was generated by
the code under test.

## 4. Differential tests

For a lifted function:

1. Run the original bytes in an isolated CPU emulator (Unicorn) with recorded inputs.
2. Run the lifted C with the same inputs in the driver.
3. Compare registers, flags, memory and the CRC of the touched regions.

`pipeline/difftest.py` is the starting point. A mismatch is a lifter or runtime bug; fix it before
touching the program logic.

## 5. Behavioural tests

For the host:

- a window with the expected class, size and title
- input at a known coordinate produces a known hit/click
- presentation at the target aspect ratio (screenshot compare)
- audio PCM at the API boundary matches a decoded reference
- the program survives several minutes of interaction without a crash

Record the exact command, environment, and the observed result. A screenshot without a reference
is not a comparison.

## 6. Replay

A recorded trace is valuable when it contains the inputs and the expected outputs, not just a log.
Store:

- the target digest
- the initial memory/registers
- the input events or API calls
- the expected state or output digest
- the tool and build hash

Replays must be deterministic. If a run needs wall-clock time, record the seed and the clock
source.

## 7. Clean checkout

The final check is from a clean clone:

```sh
python -m pip install -r requirements.txt
python static_shock.py doctor
python static_shock.py verify
python static_shock.py readiness
python static_shock.py build
```

`doctor` checks the target, toolchain and records; `verify` checks the manifest, inventory and
Python syntax. Generated files are rebuilt, not committed.

## What to do with a failure

1. Read the exact error; do not change several layers at once.
2. Identify the first incorrect value, not the last visible symptom.
3. Map the host address through `bin/lift.map`.
4. Compare the function with the original; add a differential case.
5. Fix the lifter, runtime or host bridge; rerun the ladder.
6. If the fix lowers correctness elsewhere, revert it.

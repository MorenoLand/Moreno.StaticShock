The shipped backend is x86-32. This document is the design for a second backend; it is not a
configuration flag on the 32-bit lifter. Mixing the two models produces silent corruption, so the
`arch` field selects one complete backend.

## Why it is a separate backend

| Concern | x86-32 | x86-64 |
|---|---|---|
| Guest address | 32-bit, fits a host pointer | 64-bit, fits a host pointer only below the user-space limit |
| Registers | 8 GPRs | 16 GPRs, 64-bit, REX prefixes |
| Stack | arguments and return address on the stack | first four args in RCX/RDX/R8/R9, 32-byte shadow space, 16-byte alignment |
| Floating point | x87 stack | SSE2 `xmm0..xmm15`; x87 only in legacy CRT code |
| Returns | `eax`/`edx`, `double` in `ST(0)` | `rax`, `double` in `xmm0` |
| Unwind | stack frames and SEH chains | table-driven unwind, no frame chain by default |
| Imports | stdcall/cdecl/thiscall | Microsoft x64 convention; no stdcall decoration |

## Guest model

Keep the same rule: a guest virtual address is a host pointer. On Windows x64 the user-space
limit is 47 bits, so an image based at `0x140000000` is directly addressable. The host must reserve
the image range before the CRT allocates the stack/heap, exactly as the 32-bit preentry does.

Registers become 64-bit globals (`r_rax` ... `r_r15`, `r_rip`, `r_rsp`, `r_rbp`). Sub-register
writes (`eax`, `ax`, `al`, `ah`, `r8d`, ...) preserve the rest. Address calculation uses 64-bit
arithmetic; `R64`/`W64` replace `R32`/`W32` in the emitted code.

The generated functions stay `void f_XXXXXXXX(void)`. A call pushes the guest return address and
calls the C function; the callee reads its arguments from the guest registers and stack. The host
C compiler never sees the guest ABI.

## Lifting

- Capstone `CS_MODE_64`.
- REX prefixes, `movabs`, RIP-relative operands, 64-bit immediates.
- `push`/`pop` are 8 bytes; `ret` pops 8.
- Flags: the same six locals, 64-bit operands.
- SSE2 is mandatory: scalar `double` in `xmm`, packed operations, `movq/movd`, conversions,
  `comisd/ucomisd`, `cvtsi2sd/cvttsd2si`.
- x87 is optional: implement it only when the target actually contains x87 instructions.

## Imports

Use the same sentinel table, but:

- Microsoft x64 argument registers: `rcx`, `rdx`, `r8`, `r9`; the rest on the stack.
- Every call reserves 32 bytes of shadow space.
- `double` returns in `xmm0`; integer/pointer returns in `rax`.
- Varargs (`printf`, `sprintf`) use the same registers and a register-save area; the import bridge
  must pass the guest's register state, not just stack words.
- Guest pointers are 64-bit; never truncate to 32 bits.

The 32-bit `S_MATHFP`/`ST(0)` special does not exist here. Add an equivalent that reads the x64
argument registers and writes `xmm0`.

## Image and build

- `pe_image.py` must accept PE32+ (`magic 0x20B`).
- The linker uses a 64-bit target (`x86_64-w64-mingw32-gcc`), `--image-base` at the guest base,
  and `.guest`/`.tail` sections large enough for the image and the program's allocations.
- Preentry reserves the guest range before the CRT starts, just like the 32-bit build.
- Stack and heap reserves are 64-bit address-space reserves; keep them below the guest range.

## Unwind and exceptions

MSVC x64 uses `.pdata`/`.xdata` unwind tables. A fault does not walk a frame chain. For the first
version, report the host context and stop; do not pretend SEH works. If the target relies on
exceptions, implement the unwinder as a separate project.

## Suggested file layout

```
pipeline/lift64.py       x86-64 instruction lift
runtime64/               registers, memory, imports, boot
build64.py               PE32+ layout and linker
```

`cfg.ARCH` selects the backend. The 32-bit files stay untouched, so a working project cannot be
broken by an incomplete 64-bit experiment.

## Acceptance

A 64-bit backend is done when a known 64-bit PE boots, maps its data, reaches its message loop,
and produces the same observable behaviour as the original under the differential tester. Until
then, `arch = "x86"` is the supported configuration.
